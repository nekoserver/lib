# SPEC: Muse 実行経路（lib/muse）と目的外使用の定義

本書は `lib/muse` の実行経路の仕様であり、同時に「目的外使用」の定義書である。
実装が本書から外れた使い方を可能にしている場合、その使い方ではなく実装が誤りである。

## 1. 目的

この経路の目的は、次の1つだけである。

> ダッシュボードから Muse Code への指示を「依頼」として受け付け、
> 受ける側ホストの承認と健全性確認を経た場合に限り、
> そのホスト上で1ターンだけ実行する。

読み取り専用の診断・状態表示（緑の区画群と diag.sh）は、この目的を支える
補助であり、それ自体は実行を伴わない。

位置づけ: この経路は緊急避難経路である。路肩のようなもので、
物理的には使えるが通常は使わない領域として用意する。通常の指示経路
（対話や通常の運用手順）が使えない場合の受け皿であり、常用は目的でも
想定でもない。常用されている状態が続くなら、それはこの経路を拡張する
理由ではなく、通常経路側に問題があるという兆候として扱う。

## 2. 経路の構成

```
[Web: dashboard/index.shtml]
   | フォーム送信（受付のみ。実行されない）
   v
[ask.cgi → sdk-ask-cgi.py] 検証のうえ承認待ちとして登録
   |  ~/.local/share/muse-sdk/pending/<id>.json（権限600）
   v
[ホストのシェル: sdk-approve.sh] ← 承認はここでしか行えない
   | (1) 整合性の再検証  (2) 診断ゲート（diag.sh、FAIL で遮断）
   v
[sdk-ask.sh（Python版）または sdk-ts-ask.sh（TypeScript版）]
   | SDK 経由で muse serve を起動し1ターン
   v
結果を依頼ファイルと監査ログへ記録
```

- Web から SDK へは直結しない。Web 側に承認の手段は存在しない。
- 実行コア（Python / TypeScript）の切り替えは、ホスト側の承認ツールの
  指定（`MUSE_ASK_IMPL`）でのみ行う。Web 側からは指定できない。
- すべての段で監査ログ `~/.local/share/muse-sdk/exec-audit.jsonl` に
  記録が残る（イベント: submitted / submit_refused / approved / rejected /
  executed / integrity_failed / diag_blocked / diag_gate_skipped）。

## 3. 正規の使い方（目的内使用）

次をすべて満たすものだけが目的内使用である。

1. 指示は Muse Code への作業指示であり、対象ワークスペースは
   受ける側ホストのホーム配下にある
2. プロファイルは `:read-only` / `:ask-me` / `:auto-review` のいずれか
3. 受付 → 承認待ち → ホスト側の承認 → 関門通過 → 実行、の順序が守られる
4. 承認は、ホストの内容を自分の目で確認できる者が、そのホストの
   シェルから行う
5. 結果と監査は、そのホストの運用確認のために使われる

## 4. 目的外使用の定義

次のいずれかに当たる使い方は、目的外使用である。技術的に可能であっても
正規の使い方にはならない。

### 4.1 承認と関門の回避

- 受ける側の承認を経ずに実行すること、およびそれを可能にする改変
  （例: ask.cgi からの直接実行、承認 CGI の新設、Web の設定への
  `MUSE_DIAG_GATE=off` / `MUSE_DIAG_CMD` / `MUSE_ASK_IMPL` の混入）
- 診断ゲートで FAIL が出ている間の実行、および診断結果を偽って
  通すこと（診断コマンドの差し替えを含む。ホスト保守のための
  差し替えは、監査に残る形でのみ許される）
- 承認待ちファイルを手書き・改竄して登録を偽ること
  （ハッシュ不一致・許可リスト外プロファイル・範囲外ワークスペースは
  承認時にすべて拒否される。これをすり抜ける改変も目的外使用）
- `:unrestricted` プロファイルをこの経路から使うこと

### 4.2 目的の外への流用

- Muse Code への作業指示以外の目的でこの経路を使うこと
  （例: 任意コマンドの実行口としての流用、他システムへの中継、
  データの持ち出し経路としての使用）
- 承認待ちや監査の仕組みを、無関係なジョブのキューやログとして使うこと
- 受付を繰り返して承認待ちを溢れさせること（上限で拒否される。
  上限の引き上げ自体はホスト側の運用判断だが、溢れさせる行為は目的外）

### 4.3 証跡の妨害

- 監査ログや依頼ファイルの削除・改竄によって、受付・承認・実行の
  痕跡を消すこと
- 監査に残らない経路を新設して実行すること

## 5. 関門の仕様

### 5.1 受付時（sdk-ask-cgi.py）

- プロファイル許可リスト、ワークスペースはホーム配下の実在ディレクトリ、
  指示は8000文字まで、承認待ちの上限は既定20件
- 依頼ファイルは権限600、置き場所は700で作る

### 5.2 承認時（sdk-approve.py）

- 整合性の再検証: プロファイルの許可リスト、ワークスペース
  （symlink 解決後にホーム配下で実在すること）、指示の SHA-256 が
  登録時と一致すること、長さ上限。不一致は `integrity_failed` として
  監査に残し、実行しない
- 診断ゲート: `diag.sh -s`（DIAG_QUICK=1）を走らせ、終了コード2
  （FAIL）なら実行せず、依頼は承認待ちのまま残す。1（WARN）は
  記録して通す。0はそのまま通す
- 二重承認はできない（承認待ちでない依頼は拒否される）

### 5.3 実行時

- プロファイルは SDK 側でも require で必須とし、適用されなければ
  黙って落とさずエラーにする（読み戻し確認はその例外処理としてのみ）
- 結果は依頼ファイルに status と一緒に保存され、監査の `executed`
  イベントと対応する

## 6. 状態と検証

- 本書の関門は、muse-vm 上で CGI 呼び出しの模擬と承認ツールにより
  実証済み（遮断・改竄拒否・手書き依頼の拒否・受付上限・二重承認の
  拒否・TypeScript 版コアでの承認実行を含む）
- Apache 実機での SSI/CGI 動作は未検証。配置先では、実行系を
  vhost の認証・許可リストの内側に置くことが前提である
- Muse 本体が未サインインの間、実行は `authRequired` で終わる。
  これは関門の失敗ではなく、実行段の前提不足である

## 7. 本書の変更

本書の定義を緩める変更（特に関門の撤去、承認の経路追加、目的の拡張）は、
黙って行わない。変更する場合は本書と実装を同時に変え、その旨を
コミットメッセージに明記する。
