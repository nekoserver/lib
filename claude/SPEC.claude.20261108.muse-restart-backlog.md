## 1. 背景

**対象**: Museへの問い合わせのうち、muse-vmが止まっている間に送れなかったもの — 再起動の後に、新しい問い合わせより先に片付け、片付いたら利用者に知らせる（利用者の提案、2026-11-08）。

- muse-vmは数時間おきにVMの外から強制的に再起動され、起動から応答まで約6分かかる（`n-vm-boot-wait`）。
- 止まっている間に溜まるのは2種類。本体側の順番待ちのファイル（`muse-queue/pending`）と、libのworkerで`muse_connection_failed`になったジョブ。後者は質問の本文をworkerが保存しないので、そのままでは送り直せない。
- 今の`muse_connection_failed`だけでは、「届かなかった」と「処理されたが応答が消えた」を区別できない（Codex）。

## 2. 案（CodexとMuseの一致点）

| 点 | 案 |
|---|---|
| 対象 | 本体側の順番待ちに一本化する。workerで接続に失敗した問い合わせは、呼び出し側（`inquiry.py`）が本文ごと順番待ちに積み直す |
| 順番 | 復旧した時点で溜まっている分を確定し、元の受付順（古い順）に1件ずつ送る。新しい問い合わせはその後ろ |
| 識別 | 問い合わせごとに固定のID（冪等キー）を付け、状態（待機・送信中・成功・失敗・要確認）をファイルに残す |
| 応答が分からないもの | 自動では送り直さず「要確認」にする。Museの側で固定IDによる重複の排除ができるようになったら、同じIDで送り直す |
| 再起動の検知 | `/health`の不通→復帰。可能ならMuseの起動ID（`/proc/sys/kernel/random/boot_id`）の変化で確かめる |
| 片付いたと判断する条件 | 確定した滞留分がすべて成功か失敗になり、送信中と要確認が0件 |
| 知らせる | 片付いた後に1回だけ。件数、成功・失敗・要確認の内訳、復旧からの所要時間、失敗のIDと理由 |
| 知らせる先 | Claude Codeのセッション（Monitorの通知）。利用者がいないときの通知先（Slackなど）は6章で決める |

## 3. Museの側で手伝えること（Museの申し出、未実施）

- 起動時に、起動IDと時刻を知らせる口（または`/health`に起動IDを足す）。
- 固定IDによる重複の排除と、処理状態の照会。記録は再起動をまたいで残す必要がある（`/home/hatch`だけが残る、`n-reboot-not-persisted`）。

muse-vmの変更なので、利用者の承認の後に行う。

## 4. 本体側の変更（承認後）

| ファイル | 変更 |
|---|---|
| `~/.claude/tools/muse-queue.py` | タスクに固定IDと受付時刻と状態を持たせる。送信の前に状態を「送信中」にし、応答が分からなければ「要確認」へ。不通を検知したら「復旧待ち」に入り、復帰したら滞留分を確定して処理し、片付いたら1行の要約を出す |
| `~/.claude/tools/inquiry.py` | `muse_connection_failed`のとき、本文を順番待ちに積み直す（送り直しは順番待ちが行う） |

## 5. 注意事項

- 1つのジョブの上限は300秒。待ちと送り直しを同じジョブの中で行わない（`mvr-p2`を別議題へ移した理由）。
- 「要確認」を自動で送り直すと、再実行・再課金になり得る（Codex）。
